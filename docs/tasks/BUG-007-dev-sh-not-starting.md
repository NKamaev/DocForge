## Постановка

При ручном запуске `./dev.sh` (или `bash dev.sh`) приложение не поднимается. При запуске через `bash dev.sh start` из Claude Code — запускается корректно. Пользователь не может самостоятельно запустить приложение скриптом.

## Причина ошибки

Предположительно одна или несколько из следующих причин:
1. **Нет прав на исполнение** — файл `dev.sh` не имеет флага `+x` (`chmod +x dev.sh` не выполнялся)
2. **Вызов без аргументов** — по умолчанию (`CMD=${1:-restart}`) скрипт делает `restart`, что сначала останавливает всё. Если backend не запущен, `stop_backend` завершается нормально, но `start_backend` может падать из-за незаконченной предыдущей сборки (`.gradle` lock)
3. **Таймаут 120 с недостаточен** — цикл ждёт 60 × 2 с = 120 с, при первой сборке Gradle может занимать больше
4. **`set -e` обрывает скрипт** — если любая команда вернула ненулевой код (например, `pkill` когда нет процессов), скрипт прерывается. Сейчас `pkill` защищён `|| true`, но могут быть другие места
5. **Путь к `gradlew`** — если скрипт вызван не из корня проекта, `cd "$PROJECT_DIR/backend"` может не работать корректно при некоторых конфигурациях shell

## Этапы

1. Проверить флаг исполнения: `ls -la dev.sh`
2. Запустить `bash -x dev.sh` и изучить трассировку при ручном вызове
3. Изучить логи при падении: `/tmp/docforge-backend.log`, `/tmp/docforge-frontend.log`
4. Исправить:
   - Добавить `chmod +x` в README или в сам скрипт (self-bootstrap)
   - Увеличить таймаут backend до 180 с (90 итераций × 2 с)
   - Заменить `set -e` на явную обработку ошибок в критических местах
   - Добавить проверку `chmod +x` перед `./gradlew`
5. Протестировать: `bash dev.sh start` с нуля (без прогретого Gradle кэша)
