## Интерпретация

После реализации BUG-005 (кнопка истории + автоствосохранение ревизий) и исправления backend-бага (OffsetDateTime → Instant) функционал ревизий технически работает, но требует аудита по нескольким осям:

1. **Корректность** — всё ли работает в edge-кейсах (первая ревизия, concurrent saves, restore, отсутствие body).
2. **Нагрузка на БД** — каждое автосохранение ответов (debounce 500ms) создаёт ревизию; при активной работе это сотни записей в `document_revision` (PostgreSQL) и `document_revisions` (MongoDB) за сессию.
3. **Очистка** — нет механизма удаления старых ревизий; база будет расти бесконечно.
4. **Алгоритм неактуальности** — нужно определить, когда ревизия считается «устаревшей» и может быть удалена.

## Вопросы для исследования

### A. Работоспособность

- [ ] Проверить happy-path: смена ответа → ревизия создаётся → Drawer показывает → Restore работает.
- [ ] Edge: что происходит при restore, если `currentBody = null` (TASK-006-1 ещё не выполнена)?
- [ ] Edge: concurrent autosave — два debounce-таймера гонятся одновременно (можно ли получить дубли?).
- [ ] Edge: что если `saveAnswers` вернул ошибку — `saveRevision` не вызывается (корректно).
- [ ] Edge: первый документ без единой ревизии — Drawer показывает «Ревизий ещё нет» (корректно).
- [ ] Проверить `restoreRevision`: восстанавливаются ли `answers` корректно после reload.

### B. Нагрузка на БД

- [ ] Оценить объём записей при типичной сессии (30 мин, ~60 изменений → 60 ревизий).
- [ ] Размер одной записи в MongoDB (`document_revisions`): `answers` — объект ~1КБ, `body` — JSON ~50КБ.
- [ ] При 100 пользователях × 60 ревизий = 6 000 ревизий/сессия — приемлемо?
- [ ] Индекс `idx_doc_revision (document_id, revision_number DESC)` — достаточен?
- [ ] Изучить: стоит ли добавить `TTL index` в MongoDB для автоудаления старых тел.

### C. Способы минимизировать нагрузку

- [ ] **Rate-limiting ревизий**: не создавать новую ревизию, если предыдущая была менее N секунд назад.
- [ ] **Delta-only**: хранить только diff ответов, а не полный snapshot (сложность реализации vs экономия).
- [ ] **Max ревизий на документ**: хранить не более K последних (скользящее окно).
- [ ] **Дедупликация**: не создавать ревизию, если answers/body не изменились с последней ревизии.

### D. Очистка неактуальных ревизий

- [ ] Разработать алгоритм определения «неактуальности»:
  - Старше N дней?
  - Ревизий больше K на документ → удалять самые старые?
  - Документ в статусе EXPORTED → все ревизии устарели?
  - Ревизия старше текущей на M позиций?
- [ ] Механизм очистки: background job (Spring Scheduler) или ручная команда?
- [ ] Нужен ли UI для управления ревизиями (удаление конкретной ревизии)?
