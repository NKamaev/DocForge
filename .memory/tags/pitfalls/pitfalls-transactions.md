# Pitfalls — транзакции и Spring

> Тег: `pitfalls:transactions` · Обновлён: `2026-10-24`

## Класс проблем: проглоченное исключение отравляет транзакцию

### BUG-061: `catch` вокруг вложенного `@Transactional`-метода
- **Симптом:** бизнес-метод отрабатывает без ошибок, но на коммите вылетает
  `UnexpectedRollbackException: Transaction silently rolled back because it has
  been marked as rollback-only`. В тестах это выглядит как «падение на
  коммите», хотя в коде исключение было поймано.
- **Корень:** вложенный `@Transactional` (propagation `REQUIRED`) **присоединяется**
  к транзакции вызывающего. Если из него вылетело исключение, интерсептор
  помечает **общую** транзакцию как rollback-only — `catch` в вызывающем методе
  это не отменяет, только прячет первичную ошибку.
- **Типичные места:** best-effort-атрибуция (`currentUserId()` по логину из
  security context), разрешение автора, «мягкие» справочные данные.
- **Правильное решение:** не бросающий API (`Optional<UserDTO> findUser(login)`)
  вместо `getCurrentUser()` + `catch`. Исключение в логе — признак того, что
  вызывающий код ждёт «не может быть ошибки»; сделай это явным в контракте.
- **Проверка:** `catch (Exception)` внутри `@Transactional` — искать во всех
  сервисах (см. TASK-068, BUG-071).
- **Тесты:** unit-тест на моках **не** показывает проблему (нет прокси → нет
  транзакции). Нужен IT, где пользователя нет в `users` (например
  `@WithMockUser("unknown")`) — иначе баг живёт незамеченным.

### Смежное: аудит и «глотание» ошибок (BUG-071)
- `AuditServiceImpl.log` — `@Async` + `REQUIRES_NEW` изолируют бизнес-транзакцию
  (это работает), но `catch` **внутри** транзакционного метера означает, что
  при ошибке вставки запись всё равно теряется, а наверх уходит
  `UnexpectedRollbackException`.
- **Решение (коммит `d022936`):** транзакция вынесена в отдельный бин
  (`AuditLogWriter`), `catch` живёт **вне** транзакционной границы.
- **Вторая половина проблемы:** колонка `audit_log.details` — `jsonb`, а
  вызывающие передают произвольный текст → `invalid input syntax for type json`.
  Любые «свободные» строки в JSON-колонку нужно нормализовать на границе записи
  (валидный JSON — как есть, прочее — заворачивать), иначе запись теряется
  молча. См. `tickets/BUG-071.md`.
